# 0020: one server, reached only through SSM

Date: 2026-09-15

## Status

Accepted.

## Context

Phase 5 asks for a hosted testhunch: Postgres, the API, and object storage for the raw reports, on
one server described by Terraform. The roadmap said to build it locally first and move it to a cloud
afterwards; the maintainer has an AWS account and chose to go straight there, so the first
`terraform apply` runs against real, billable infrastructure.

Three things shape the decision. The API authenticates with a bearer token, so plaintext transport
would hand that token to anyone on the path. The project is a side project paid for out of about
100 dollars of credit, so a bill of tens of dollars a month is the difference between a deployment
that survives and one that gets torn down. And the image published by `release.yml` is built without
a `platforms:` list, which makes it `linux/amd64` only.

## Decision

One `t3.small` EC2 instance in `eu-west-3`, running Postgres, the migration and the API as
containers under a single systemd unit. The root volume holds the Postgres data and is encrypted.
An S3 bucket is provisioned for the raw reports, with public access blocked, versioning on, and the
instance allowed to read and write it.

**The security group has no inbound rule at all, and there is no SSH key.** The instance is reached
through SSM Session Manager, which dials out. To use the API, a port forward brings port 8000 to the
operator's own loopback. Nothing about the API is exposed to the internet, so no certificate is
needed yet and the token never travels in the clear.

The Postgres password and the API token are generated by Terraform and kept in SSM Parameter Store
as `SecureString`. The instance reads them once at first boot, through its instance role, into a
file only root can read. They are not in the user data, which any process on the instance can read
back from the metadata service.

x86, not Graviton, and a variable validation refuses a `t4g.` or `m7g.` instance type with the
reason: an arm64 instance would pull an image it cannot run, and the failure would only appear in
the container logs, long after `terraform apply` reported success.

## Consequences

The running cost is about 18 dollars a month: roughly 16 for the instance and 2 for the volume, with
the bucket in the pennies. The credit covers around six months.

Nobody can reach this deployment without AWS credentials for the account, which is the point tonight
and a limit tomorrow: a GitHub Action cannot send its history to it. Publishing the API needs a
domain name, a certificate and an inbound rule, and that is a separate decision with its own ADR.

Postgres in a container on the instance's own disk means backups are ours to arrange: there is no
automated snapshot, and destroying the instance destroys the history. Moving to RDS later changes
`TESTHUNCH_DATABASE_URL` and nothing else in the application.

The object storage is provisioned but unused: the API stores results in Postgres and keeps no copy
of the XML it was sent. The bucket exists so that the code which will write to it has somewhere to
write, not because anything writes today. Saying otherwise in the documentation would be a claim
without a measurement behind it.
