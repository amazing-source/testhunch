# 0021: the API answers on one public name, behind a certificate it gets itself

Date: 2026-09-15

## Status

Accepted. Relaxes [ADR 0020](0020-one-server-reached-only-through-ssm.md), which opened nothing.

## Context

ADR 0020 gave the server no inbound rule at all, which was the right posture for a deployment
nobody but its operator needed to reach. Phase 5 then asks for something that posture forbids: that
testhunch's own CI send its history to the hosted API.

Two ways to get there. The CI could take temporary AWS credentials through OIDC, open an SSM
tunnel from inside the job, and talk to the API over the loopback, leaving nothing open. Or the API
could answer on a public name behind a certificate. The first keeps ADR 0020 intact but only ever
serves a client that can assume a role in this AWS account, which a hosted service cannot require of
the repositories it is meant to serve. The maintainer registered `testhunch.xyz` and chose the
second.

## Decision

The instance gets a fixed address, and ports 80 and 443 are opened to the internet. Caddy runs in
front of the API, obtains the Let's Encrypt certificate itself and renews it on its own. The API
container publishes nothing but its loopback port: Caddy reaches it over the compose network, so
the only thing listening on the public address is the proxy.

All of it is conditional on `api_domain`. Empty, and nothing is reserved, nothing is opened, and the
server is exactly what ADR 0020 describes. That is what makes this a relaxation and not a rewrite:
the closed deployment is still one variable away.

## Consequences

**The bearer token is now the only thing between the internet and the database.** It is 48 random
characters, generated by Terraform and never written to the repository, and the API answers 401
without it. But it is one token shared by every client, so it cannot be revoked for one repository
without revoking it for all. Per-repository tokens were a phase 5 item before this ADR; they are the
next one after it.

There is no rate limiting. A stolen token gets the whole history, and an unauthenticated flood still
costs CPU on a `t3.small`. Neither is addressed here.

The certificate depends on a DNS record the project does not own in code: `api.testhunch.xyz` points
at the address by hand, at the registrar. If that record moves, Caddy keeps serving the certificate
it has until renewal fails, silently, for up to thirty days.

**Changing the instance's user data replaces the instance, and the Postgres volume goes with it.**
That was free while the database was empty. It will not be once the CI sends anything worth keeping,
and the way out is either a volume that outlives the instance or a managed database. Until that is
fixed, every change to the server's startup script is a data loss.
