```bash
cargo nextest run -E "$(testhunch select \n  --budget 25% --runner nextest --base origin/main)"
```

La sortie est un filterset, par exemple :

```text
not ((binary_id(=shop) & test(=tests::sums_prices)) | ...)
```

S'il n'y a rien à écarter, la sortie est `all()`.

## Pourquoi le `=` partout

Les correspondances par défaut de nextest attrapent trop : glob pour les identifiants de binaire, et
« contient » pour les noms de test. Le matcher d'égalité `=` est exact, et la référence du langage
demande aux programmes qui construisent des expressions de toujours préciser un matcher. testhunch le
fait donc systématiquement.

Vérifié avec de vraies exécutions de cargo-nextest 0.9.144 (`tests/fixtures/select/nextest`), y
compris le cas de tests homonymes dans un autre binaire.

## La limite à connaître

Une clé nextest ne peut pas être redécoupée en identifiant de binaire et nom de test, parce que les
deux peuvent contenir `::`. testhunch utilise donc comme identifiant de binaire la **suite**
enregistrée depuis le `classname` du rapport. Un test dont la suite ne préfixe pas la clé n'est pas
visé, donc il tourne.
